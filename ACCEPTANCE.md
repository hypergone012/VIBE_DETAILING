локальный Supabase (CLI 2.120, Postgres 17, Edge Runtime 1.77 / Deno 2.1) в Docker,

## Требования → чем подтверждено

### 1. Одна сборка, один проект Supabase, `tenant_id` везде, `/s/{slug}/` и `/s/{slug}/owner/`
- Две демо-студии из одного `dist/` с разными оболочками, иконками, manifest, акцентом —
  `tenant:verify` 10/10 обе; e2e `pwa.spec.ts` (разные scope SW и кэши).
- Третья студия создана и опубликована **без изменения исходников** за 36 с машинного
  времени (`tenant:new → validate → publish → build → verify --browser` 10/10); первые две
  после этого — 9/9 без браузерной проверки. Пробная студия затем удалена из репозитория.
- SQL: «a second studio is created next to the first, never replacing it»; составные FK
  `(tenant_id, id)` — «a service of studio A cannot be linked or booked through studio B».

### 2. `business.json` + фото — вход, БД — источник; `tenant:new/validate/publish/verify`
- Все четыре команды в `package.json` и выполнены (см. п. 1); integration `pipeline.test.ts`:
  создание папки, отказ перезаписать существующую, публикация образца с владельцем,
  переиздание сохраняет правки владельца, новая студия не влияет на старые.

### 3. Непрерывная занятость ресурса, несколько дней и буфер, часы/исключения/таймзона
- SQL `slots.test.ts`: часы в поясе студии (не UTC), выходные и особые часы, запас времени
  и горизонт, многодневные услуги с выдачей в рабочее время, границы суток через полночь UTC,
  буфер подготовки в диапазоне занятости.
- SQL `booking.test.ts`: «a two-day service occupies its box across both days»;
  «fills two suitable resources, then reports the slot as taken».

### 4. Одна `resource_occupancies` с EXCLUDE; атомарность; идемпотентность; перенос не теряет запись
- SQL `concurrency.test.ts`: из 16 одновременных клиентов на один бокс успешен ровно 1; на
  два бокса — ровно 2 и в разные боксы; пересекающиеся диапазоны; один ключ идемпотентности
  ×10 параллельно → одна запись и один токен; гонка двух переносов; запись владельца против
  записи клиента.
- SQL `booking.test.ts`: блокировка и запись взаимно исключают друг друга; перенос атомарен
  и при занятом времени исходная запись остаётся; клиент не может задать цену/студию/длительность.
- В интерфейсе: занятое время зачёркнуто; ошибка блокировки бокса показывает конфликтующую
  запись (проверено в браузере).

### 5. Без регистрации; токен записи (в БД только хэш, тот же при повторе); вход владельца без регистрации
- SQL: токен открывает только свою запись и только в своей студии; владельцы не читают хэши.
- Integration: публичная регистрация отключена (GoTrue); владелец одной студии читает
  только её; загрузка в Storage — только в папку своей студии.
- E2E `booking-flow.spec.ts`: клиент выбирает услугу и свободное время, подтверждает,
  запись видна в «Моя запись»; владелец входит в кабинет и находит её по коду (телефон и десктоп).
- Выход владельца удаляет сессию из `localStorage`, очищает приватные запросы и кэши SW
  (проверено в браузере; ключ `owner-auth:<slug>` пропадает).

### 6. RLS, составные FK, строгие GRANT; anon не видит персональные данные; секреты на сервере
- SQL `rls.test.ts` и integration `api.test.ts`: anon не читает ни одну таблицу, не вызывает
  приватные/служебные RPC; публичные данные студии без персональных; полезная нагрузка
  задач рассылки без телефона и имени.
- В клиентском бандле нет service-role, LLM-ключа и приватного VAPID (только `VITE_*`).
- E2E `pwa.spec.ts`: ни один ответ `/rest|/auth|/functions` не попадает в кэши SW.

### 7. Помощник: LLM_BASE_URL/LLM_API_KEY/LLM_MODEL, инструмент до ответа, разделение режимов, ограниченный цикл, JSON-fallback
- Unit `router.test.ts` (27): роутер намерений отдельно — клиентские и владельческие
  вопросы, услуги в любом падеже, даты в календаре студии, ключи периодов как в SQL.
- Unit `engine.test.ts` (13): обязательный инструмент выполняется до модели и передаётся ей
  как tool output; модель вне режима не получает инструменты владельца, запрос на них
  отклоняется без чтения данных; аргументы — только период/услуга/дата; цикл ≤ 3 раундов
  (последний без инструментов); JSON-intent fallback; шаблонный ответ без модели или при сбое.
- Integration `assistant.test.ts` (9): реальная БД + **реальный OpenAI SDK** + фейковый
  OpenAI-совместимый сервер: модель получила реальные свободные окна; инструменты по запросу
  модели; 400 «tools not supported» → JSON-режим; 503 → шаблон; владелец без входа → 401,
  чужой студии → 403; деньги и заезды — из `owner_stats`; лимит 20 вопросов на IP → 429;
  бюджет токенов сверяется с usage провайдера.
- **В настоящем Supabase Edge Runtime (Deno)**: функция `assistant` поднята через
  `supabase functions serve`, ответила реальными данными в режиме без модели, а с
  `LLM_BASE_URL` на фейковый endpoint — вызвала его через `npm:openai` с клиентскими
  инструментами; в браузере работают чат клиента и чат владельца (сумма за неделю в чате
  = сумма на экране «Деньги», 41 500 ₽ за 5–11 октября).

### 8. Статистика в SQL; заезды / выполнено / получено раздельно; «запланировано» ≠ выручка; один период и пояс
- SQL `payments-stats.test.ts`: раздельные показатели; границы периода в поясе студии тем же
  резолвером, что у помощника; возвраты не больше полученного, в том числе параллельно.
- Кабинет «Деньги»: блок «Запланировано на период» с пояснением, что это не выручка.

### 9. Свои метаданные, manifest, иконки, maskable, apple-touch, заставки; отдельные scope и кэши; глубокие ссылки
- `tenant:verify` (обе студии): оболочка студии на глубоких ссылках, кабинет noindex со своим
  manifest, id/start_url/scope, иконки any+maskable, apple-touch 180×180 без прозрачности,
  12 заставок iOS, SW со scope студии, **Chrome не сообщает ошибок установки** (CDP
  `Page.getInstallabilityErrors` в обычном профиле).
- E2E `pwa.spec.ts`: офлайн открывается оболочка студии и **глубокая ссылка другой студии**
  с её акцентом и названием, с плашкой «Нет подключения».

### 10. Web Push (VAPID) + Supabase Cron + outbox (lease, дедупликация, перенос/отмена); ICS; честные состояния
- SQL `outbox.test.ts`: одно напоминание за 24 ч, без дублей; lease — два воркера не берут
  одну задачу, завершает только держатель; истёкший lease, повтор с backoff, «gone» отзывает
  подписку; перенос отменяет старую задачу и создаёт новую; отмена записи отменяет задачу;
  cron-задачи созданы в pg_cron.
- Unit `webpush.test.ts`: наше шифрование RFC 8291 **расшифровывает эталонная `http_ece`**;
  подпись VAPID (RFC 8292) проверяется публичным ключом; классификация ответов push-сервиса.
- Integration `push.test.ts` (9): доставка зашифрованного напоминания на фейковый push-сервис
  и расшифровка как в браузере; 3 параллельных диспетчера — каждое напоминание ровно один раз;
  перенос, отмена, 410, 503 с backoff, образец не отправляет, секрет cron и отсутствие VAPID.
- **Вся цепочка вживую**: Supabase Cron (02:52:00) → pg_net → Edge Function
  `notifications-dispatch` в Deno → зашифрованное сообщение на фейковый push-сервис →
  расшифровано («Сегодня в 11:00 — Мойка… Код записи 3EEY6N»), задача `sent`
  (`scripts/dev/check-cron-push.ts`).
- E2E: на iPhone во вкладке браузера — подсказка установить приложение, кнопки «Напомнить»
  нет, «Добавить в календарь» есть. ICS — unit-тест формата (экранирование, напоминание за сутки).

### 11. Образец только с демо-данными, без реальных уведомлений; live после проверки; переиздание сохраняет записи и фото владельца
- SQL `pipeline-limits.test.ts`: активация требует данных и удаляет демо-записи образца;
  переиздание сохраняет записи, правки и фото владельца; невалидный конфиг отклоняется до изменений.
- Integration `push.test.ts`: подписка в образце → состояние `preview`, задача пропущена
  `preview_tenant`, на push-сервис ничего не ушло.
- В браузере: замена одного фото в кабинете меняет только его (5 остальных не тронуты),
  подпись и новое фото сразу видны на странице клиента.

### 12. Общие атомарные счётчики лимитов и бюджета LLM; запись работает без AI
- SQL: счётчики атомарны под конкуренцией и упираются в лимит; неудачные попытки записи
  тоже считаются; параллельные резервы бюджета не превышают дневной лимит студии.
- Помощник без модели или при её падении отвечает шаблоном; запись от него не зависит
  (e2e записи выполняются с выключенной моделью).
